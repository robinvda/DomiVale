# CLAUDE.md

## Project overview

DomiVale is a small, turn-based kingdom game in Flutter/Flame: every district
you add to a city claims the land around it, so growing a city is drawing a
border, and the land you hold at the end is the score. It is built on
`vale_engine`, the shared engine behind the Vale games, and shares LogiVale's
and LumaVale's setting, fonts and UI chrome.

`DESIGN.md` holds the full design document, the starting numbers and the
phased roadmap. This file holds the engineering rules.

**Status: Phase 0 and Phase 1 done, Phase 2 next.** The app boots to a main
menu. The rules core is written and tested: board, reach, claiming, cities,
districts, yields, basic piles, turns, crowns, and a match as header plus log.
Nothing is drawn on screen yet.

## Engineering philosophy

- **Reuse and extend** existing systems rather than building parallel ones.
- **Understand before changing.** Read the code and `DESIGN.md` section for
  the area you are about to touch.
- **Minimal surface area.** No abstractions, helpers or configurability beyond
  what the task requires.
- Code and comments are always in English. Comments describe what the code
  currently does, for a reader who knows only the current state.
- Prefer the simplest thing that is exactly right at this scale. A 32×32
  board is 1024 cells; a straight loop over all of it is usually both clearer
  and fast enough.

## The rules are a separate, pure Dart package

`packages/domivale_rules` is the single most important structural decision,
because of the multiplayer plan (`DESIGN.md` §3.1). It is a path dependency
of the game and **imports nothing from Flutter, Flame or `vale_engine`**, so
the same code runs in the game, in the bots, in tests, and later on a server.

Rules that follow, each of which costs a bug when missed:

- **A match is data plus a log.** `Match` is a `MatchHeader` (rules version,
  board, house setups, seed) and an ordered list of `Action`s.
  `MatchState.replay(header, log)` is pure: same header, same log, same state,
  on every platform. A log is a record of accepted actions, so an action the
  rules refuse during a replay is a `StateError`, not a result.
- **The board is data in the match**, not generated by the rules. The
  generator lives in the game and its output is stored in the header.
- **Integer arithmetic only, and our own random numbers.** On the web a Dart
  `int` is a JavaScript double. The rules keep every value small, use no
  bitwise operations, and shuffle with `Prng` (Park-Miller, in `cards/`)
  rather than `dart:math`. The reach rule is written as
  `4(dx² + dy²) <= (2r + 1)²` for the same reason. The rules tests run in
  Chrome as well as on the VM in CI, and `replay_test.dart` pins a
  fingerprint of a scripted match that both must reproduce.
- **Every action is validated by the rules, not by the UI.** The UI asks
  `offeredCells` what is legal and sends an `Action`; `apply` accepts or
  refuses it and a refused action changes nothing. The UI never mutates state.
  `_placementRefusal` is shared by `apply` and `offeredCells`, so what the
  game highlights is exactly what the rules accept.
- **Derived values are never stored.** Yields, prices, crowns, offered cells
  and standings are computed from the state on demand. `House` holds goods,
  hand and renown; `City` holds its heart and districts; `MatchState` holds
  per-cell owner and city. Nothing else.
- **Every tuned number lives in `rules.dart`** (`Rules`) or on the card table
  (`CardKind`). Nothing elsewhere repeats a value from the "Starting numbers"
  table in `DESIGN.md` §13.
- **Undo is forgetting the end of the log.** `Match.truncate` and a replay. No
  state is unwound by hand.

`apply.dart` is a `part` of `match_state.dart` so it can reach the state's
private fields while staying its own file; `scoring.dart` is an extension on
the public queries.

## The engine boundary

`vale_engine` is a private package consumed by git URL and pinned through
`pubspec.lock`. Breaking its public API breaks LogiVale and LumaVale, so **any
change there is additive**. Nothing in the engine may know about a game.

For side-by-side development, add an untracked `pubspec_overrides.yaml`. This
repository does not sit next to the engine, so the path is
`../robinvda/vale_engine`, not `../vale_engine` (see `README.md`).

**Check `pubspec.lock` before every commit.** With the override in place,
every `flutter pub get` rewrites the engine stanza to `source: path`. The
committed lock must keep `source: git` with its `resolved-ref`, because CI
resolves the engine from it. Never stage that rewrite: leave the file
modified in the working tree, or `git restore pubspec.lock`. Don't use
`git commit -a` here.

What DomiVale uses from the engine, and what it deliberately does not (no
pathfinding, no fog, no `TerrainPass`), is in `DESIGN.md` §2.

`buildRadiusCellPath` matters twice: its distance rule is the rules' reach
rule, and `test/world/reach_test.dart` checks the two agree; and called with
radius 0 on every owned cell it outlines a territory.

## Performance

Mobile-first. Never allocate a `Paint`, `Path`, `List`, `Rect` or
`TextPainter` inside `render()` or `update()`; pre-allocate as fields. Every
renderer culls to the visible rect. Rendering never mutates simulation state.

## Voice and copy

Warm and low-pressure, as the other Vale games. Conquest is told plainly and
without blood: "The Lake House took your mill by the river." No "Warning" or
"Error" in player-facing text, no all-caps. `Refusal.message` carries the
line the game shows for each refused action.

Name: `DomiVale`, one word, capital D and V. Tagline: `settle · grow · rule`.
